From Wallet Seed to Ethereum Address

Hashing, key derivation and cryptographic primitives in the Ethereum wallet pipeline

1. Overview

An Ethereum wallet is, at its core, a deterministic program that turns one secret (a random number, shown to the user as a mnemonic phrase) into an unlimited family of accounts. No single algorithm does everything: the pipeline chains several primitives, each solving a different problem: encoding randomness for humans, stretching it into a seed, deriving a tree of keys, linking private and public keys, compressing the public key into a short identifier, and protecting that identifier against typos.

2. The standards and primitives

BIP-39 — mnemonic sentence and seed

Entropy of ENT bits (128 to 256) is extended with a checksum made of the first ENT/32 bits of its SHA-256 hash. The result is cut into 11-bit groups, each indexing a 2048-word list: 128 + 4 = 132 bits gives 12 words, 256 + 8 = 264 bits gives 24 words. The mnemonic is then converted into a seed with PBKDF2-HMAC-SHA512, using the mnemonic as the password, the string "mnemonic" + passphrase as salt, 2048 iterations and a 512-bit output. The optional passphrase (the "25th word") produces a completely different wallet; an empty passphrase is the default. Note that the word list is an encoding of the entropy, not an encryption of it.

BIP-32 — hierarchical deterministic (HD) derivation

The master node comes from I = HMAC-SHA512(key="Bitcoin seed", data=seed): the left 256 bits are the master private key, the right 256 bits the chain code. A child is computed as I = HMAC-SHA512(chain_code_parent, data‖index), with child key (I_L + k_parent) mod n and the new chain code I_R. Indexes ≥ 231 are hardened: the data includes the parent private key, so a leaked child key plus the parent public key cannot reveal siblings. Non-hardened indexes use the parent public key, which enables watch-only wallets (xpub). The whole tree is reproducible from the single seed, so only one backup is needed.

BIP-44 — standard derivation paths

BIP-44 fixes the meaning of the levels: m / purpose' / coin_type' / account' / change / address_index. Ethereum uses coin type 60 (registered in SLIP-44), so the first account of most wallets is m/44'/60'/0'/0/0, the second m/44'/60'/0'/0/1, and so on. Thanks to this convention the same mnemonic gives the same addresses in MetaMask, Rabby, Rainbow, Exodus or a hardware wallet. (Some wallets use variants such as Ledger Live's m/44'/60'/x'/0/0, which is why imports sometimes show "different" addresses.)

secp256k1 — elliptic-curve public-key cryptography

secp256k1 is the curve y² = x³ + 7 over the prime field with p = 2²⁵⁶ − 2³² − 977, with a fixed generator point G of prime order n ≈ 2²⁵⁶. The public key is K = k·G (scalar multiplication). Computing K from k is fast; recovering k from K is the elliptic-curve discrete logarithm problem, believed to need about 2¹²⁸ operations. Ethereum uses it for ECDSA signatures with public-key recovery: a transaction signature (r, s, v) lets nodes recover the signer's public key, and hence the sender address, without it being transmitted.

Keccak-256 — the hash function

Keccak is a sponge construction (rate 1088 bits, capacity 512 bits for the 256-bit variant). Ethereum computes address = last 20 bytes of Keccak-256(X‖Y), where X‖Y are the 64 bytes of the uncompressed public key without the 0x04 prefix. Hashing here gives a shorter identifier (160 instead of 512 bits) and hides the public key until the account first signs a transaction.

EIP-55 — mixed-case checksum

Take the lowercase hex address (no 0x) as ASCII text and compute its Keccak-256. For each hex letter at position i, write it in uppercase if the i-th hex digit of the hash is ≥ 8, otherwise lowercase. Digits are unaffected. The address stays backward compatible (all-lowercase still parses), but a wallet can now detect most typos by recomputing the casing. The EIP estimates about 15 check bits per address on average and a probability of roughly 0.0247% that a random mistyping passes unnoticed.

3. Chronological context

  • 1977 — RSA. First widely used public-key scheme (factoring). Ethereum does not use it, but it opened the era of asymmetric cryptography; elliptic curves (1985, Koblitz and Miller) later offered the same security with much shorter keys.
  • 2001 — SHA-2 / SHA-512. NIST hash family (Merkle–Damgård). Used inside PBKDF2 and HMAC for BIP-32/39, and SHA-256 for Bitcoin.
  • 2012 — BIP-32. HD wallets: one seed, a tree of keys. (Keccak also wins the NIST SHA-3 competition in 2012.)
  • 2013 — BIP-39. Human-readable mnemonic and seed generation.
  • 2014 — BIP-44. Multi-account, multi-coin path convention.
  • 2015 — SHA-3 (FIPS 202). Standardization of Keccak. Ethereum went live in 2015 using the original Keccak, before the final padding change.
  • 2016 — EIP-55. Mixed-case checksum for addresses.

The order reflects a logic: first public-key cryptography and hash standards, then wallet key-management conventions built on top of them (2012–2014), then Ethereum's own address layer (2015–2016). Ethereum therefore reused Bitcoin-era wallet standards unchanged (BIP-32/39/44, secp256k1) and replaced only the address derivation (Keccak-256 instead of SHA-256 + RIPEMD-160 + Base58Check).

4. SHA-2 / SHA-512 versus Keccak / SHA-3

Both are cryptographic hash functions but with different internal designs. SHA-2 (including SHA-512) is a Merkle–Damgård construction with a compression function; it is exposed to length-extension attacks unless wrapped (e.g. in HMAC). Keccak is a sponge: input is absorbed into a 1600-bit state and output is squeezed out; it is not vulnerable to length extension and was chosen as SHA-3 in a public competition as a structurally different fallback to SHA-2.

Keccak-256 is not identical to NIST's SHA3-256. When NIST standardized SHA-3 it appended the domain-separation bits 01 to the message before the usual pad10*1 padding (the first padding byte becomes 0x06 instead of 0x01). Ethereum had already adopted the pre-standard version. The permutation is the same, but the outputs differ:

Keccak-256("")  = c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
SHA3-256("")    = a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

Practical consequence: using a library's sha3_256 instead of keccak256 yields wrong addresses. In Ethereum tooling, "sha3" in old Solidity/web3 code usually means Keccak-256.

5. Statistical and security properties

  • Entropy and uniformity. A 128-bit mnemonic has 2¹²⁸ possibilities, a 256-bit one 2²⁵⁶. Security equals the entropy of the source, so the CSPRNG must be uniform; human-chosen phrases or "brain wallets" are statistically weak and are brute-forced in practice.
  • BIP-39 checksum. Four bits (12 words) mean a random word sequence is valid with probability 1/16, so 15 of 16 random typos are detected; 24 words use 8 bits (1/256). It detects errors but adds no security.
  • Key stretching. 2048 PBKDF2 iterations slow an attacker only about 2¹¹ times: negligible for random mnemonics, but it matters when a weak passphrase is used.
  • Pseudo-randomness of derivation. HMAC-SHA512 outputs are computationally indistinguishable from random. The chance that a derived IL is ≥ n or equals 0 is about 2⁻¹²⁷, i.e. practically never (the spec says to skip that index).
  • Private keys. Uniform in [1, n−1], n ≈ 2²⁵⁶; the search space is far beyond brute force. Best known attacks on the curve (Pollard rho) cost about √n ≈ 2¹²⁸.
  • Avalanche effect. Flipping one input bit of Keccak-256 flips each output bit with probability ≈ 1/2. Neighbouring keys give unrelated addresses, so addresses leak nothing about the key or about each other.
  • Address collisions. The address is 160 bits: preimage resistance ≈ 2¹⁶⁰, collision (birthday bound) ≈ 2⁸⁰. Accidental collisions are negligible; targeted ones would need ≈ 2⁸⁰ work, a long-term concern but far from practical today.
  • EIP-55. A 40-hex-digit address has on average 40 × 6/16 = 15 letters, so about 15 check bits; each letter's case is a quasi-random function of the hash. Errors that change digits only, or addresses with few letters, get weaker protection.

6. Why several primitives instead of one

Each step has different requirements, and no single algorithm satisfies all of them:

  • BIP-39 / BIP-32 / BIP-44 → key management. Need determinism, backup in a human-friendly form, and structure (accounts, coins). Hash/KDF functions, not signature schemes, are the right tool.
  • secp256k1 → key relation and signatures. Need a one-way structured relation between a secret and a public value so that anyone can verify a signature without learning the secret. Hash functions cannot do this.
  • Keccak-256 → hashing. Need fixed-size, unstructured, collision-resistant compression of the public key into a short identifier. Elliptic curves cannot do this.
  • EIP-55 → error detection. Need a few redundant bits that fit inside an existing format without changing it. Neither signatures nor hashes alone give typo detection; here the hash is reused as the source of check bits.

This is the principle of separation of concerns: each layer can be audited, replaced or upgraded independently (for example a future post-quantum signature scheme would replace secp256k1 but not the mnemonic layer).

7. Hands-on experiments with wallets

  • Generate a throw-away mnemonic and import it into MetaMask, Rabby and Rainbow: the first address is the same everywhere (same BIP-44 path). Exodus and hardware wallets may differ if they use other paths.
  • Add a new account: it is the next address_index in m/44'/60'/0'/0/i, derived from the same seed. Use an offline BIP-39 tool (e.g. Ian Coleman's, run locally) to display seed, xprv, path and address side by side.
  • Import the same mnemonic with a passphrase: a completely different set of addresses appears.
  • Take an address, change the case of one letter, and paste it into a send field: the wallet should warn about an invalid checksum. An all-lowercase address is accepted without check.
  • Change one word of the mnemonic: wallets reject it ≈ 15 times out of 16 because of the BIP-39 checksum.

8. Conclusion

The Ethereum wallet pipeline is a composition of well-separated tools: BIP-39 turns randomness into a memorable secret and a seed; BIP-32 and BIP-44 deterministically derive an organized tree of private keys; secp256k1 provides the public/private relation and signatures; Keccak-256 compresses public keys into 20-byte identifiers; EIP-55 adds typo protection by encoding checksum bits in letter casing. Real security comes from a single source: the unpredictability of the initial entropy, and from keeping the mnemonic and passphrase secret.
